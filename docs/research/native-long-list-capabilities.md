# Native long-list capabilities

Research for [Native long-list capabilities](https://github.com/dvcol/planner/issues/20), verified on **2026-10-08** using primary Apple documentation and the installed iPhoneOS 27 and macOS 27 SDKs. Product context is the [confirmed duration and search choices at 940d01a](https://github.com/dvcol/planner/blob/940d01ad0cd4458e91c13f0db1b78009510d72c7/docs/duration-and-search.md), the [current fixtures at the same commit](https://github.com/dvcol/planner/blob/940d01ad0cd4458e91c13f0db1b78009510d72c7/docs/search-fixtures.md), the [baseline identity fixtures in this worktree](../search-fixtures.md), and the [published native search research](https://github.com/dvcol/planner/blob/17b97dabb911caaa0998248f344ba8620cba9845/docs/research/native-search-capabilities.md).

**Recommendation:** start the focused prototype with a native List and a complete canonical query. Use a native Table where the eventual platform layout calls for columns. Compare native SwiftData batched fetching or OS 27 ResultsObserver only when measurements show that fetching or retaining models matters. The reviewed capabilities do not justify a custom moving data window before this comparison.

This report contains documentation and declaration evidence. No application, benchmark, Swift implementation, runtime paging experiment or device test was created or run. The accepted 5,000-item / 200-list dataset and results visible within 300 ms after final input are requirements, not observed results or storage caps. Smooth scrolling still requires device measurements.

## Accepted context and open decisions

The human's accepted activity conversions use fixed elapsed units: a day is 24 hours, a week 7 days, a month 30 days and a year 365 days, with one-minute precision. Maximum-duration comparisons are inclusive; unknown estimates are excluded unless enabled. These activity estimates remain separate from calendar spans. A sort selector must support alphabetical, chronological and duration order, ascending and descending.

The exact chronological field, default order, tie rules, unknown-estimate position and alphabetical locale/collation policy remain decisions in Duration and search. Core architecture must resolve refresh, snapshot and selection/scroll-anchor behavior under changes. Navigation prototype owns platform layout. No page size, moving-window size or memory budget is selected here. The immutable product-context links above contain the current choices; the worktree's earlier fixture file is retained only as a baseline identity reference.

The complete logical matching sequence must remain independent of which rows are currently visible, realized, prefetched or retained. Text still matches all typed words across accepted current item fields, combined with cumulative filters and stable shared-label identities. An item with multiple memberships appears once in global scope.

## Native containers defer rows, not the whole query

Apple documents List as loading rows as needed. Its performance session explains the separate identity pass: List and Table gather row identifiers eagerly, while List creates rows for the visible region plus a system-controlled buffer that can cover prefetching and accessibility. Cheap, stable identifiers and a constant row count per collection element let the container avoid constructing all row content to discover identities. Filtering with conditional row builders or erasing their structure can defeat that benefit. Compute logical matches outside the row builder. [List data and identity](https://developer.apple.com/documentation/swiftui/displaying-data-in-lists), [Identity and row construction](https://developer.apple.com/videos/play/wwdc2023/10160/)

This is row realization, not a documented limit on model objects, relationships, retained row state or peak memory. Feeding a complete model array into List still retains the application's array. Feeding a batched collection can cause the identity pass to access every element. That is an inference from eager identification and access-triggered batching, not a measured OS 27 outcome. A separate identity collection can be evaluated if profiling identifies model loading as the cost, but it is not required architecture here.

LazyVStack in ScrollView creates children on demand. Standard stacks construct their hierarchy together; lazy stacks defer geometry until content becomes visible. Apple recommends profiling before replacing a standard stack solely for performance. A lazy stack does not query the database, perform complete text matching or define selection and loading-error behavior. None of the reviewed documentation gives an application-selected recycling buffer or a fixed maximum of resident views. [Scrollable stacks](https://developer.apple.com/documentation/swiftui/creating-performant-scrollable-stacks/)

Table is available on all three required platforms. In compact width, including iPhone, it hides headers and all columns after the first. Mac also supports horizontal scrolling. The table's sort-order binding communicates header changes; the application must sort or fetch the underlying data. The control does not sort the dataset itself. Layout and a separate sort selector must therefore preserve the chosen query contract when table headers are unavailable. [Table behavior](https://developer.apple.com/documentation/swiftui/table)

Scroll visibility callbacks can report targets in a ScrollView configured with `scrollTargetLayout`. They are observation tools, not an infinite-loading engine or a guarantee that every List/Table uses the same scroll-target behavior. Do not treat appearance of the final rendered row as proof that the canonical query is exhausted. [Target visibility](https://developer.apple.com/documentation/swiftui/view/onscrolltargetvisibilitychange(idtype:threshold:_:))

## SwiftData's native fetching choices

| API or setting | Supported behavior | Boundary for Planner |
| --- | --- | --- |
| `fetch(descriptor)` | Returns an array of matching models. [Array fetch](https://developer.apple.com/documentation/swiftdata/modelcontext/fetch(_:)) | Straightforward baseline; array and application references can retain all results. No timing or memory bound follows from the API. |
| `fetch(descriptor, batchSize:)` | Returns FetchResultsCollection. Sequential access or subscripting automatically fetches needed batches. [Batched fetch](https://developer.apple.com/documentation/swiftdata/modelcontext/fetch(_:batchsize:)) | Native loading is already available. Visiting all models for IDs, text matching or sorting can touch all batches. The documentation does not promise automatic eviction or a global resident-model ceiling. |
| `fetchIdentifiers` and its batch overload | Fetches persistent identifiers matching the descriptor, including automatic batches. [Identifier batches](https://developer.apple.com/documentation/swiftdata/modelcontext/fetchidentifiers(_:batchsize:)) | Useful for evaluating identity-first access; identifiers do not contain accepted text fields. PersistentIdentifier is a store identity and does not replace Planner's stable item UUID contract. |
| `enumerate` | Runs a closure over matching models with batch traversal. Default batch size is 5,000; mutation guard defaults to enabled. [Enumeration](https://developer.apple.com/documentation/swiftdata/modelcontext/enumerate(_:batchsize:allowescapingmutations:block:)) | Suitable for complete scans or processing, not automatically a live scroll collection. Keeping model references can defeat a traversal's intended memory benefit. The default is an API default, not an approved page size. |
| `fetchCount` | Returns the number of models satisfying a fetch descriptor. [Count](https://developer.apple.com/documentation/swiftdata/modelcontext/fetchcount(_:)) | A count for a coarse store predicate is not the final count after extra canonical lexical filtering. Verify any use of descriptor limits, offsets or unsaved changes against the real store. |
| `fetchLimit` / `fetchOffset` | Limit bounds returned models; `nil` means all, not zero. Offset skips matching models and combines with a limit to select a subrange. [Limit](https://developer.apple.com/documentation/swiftdata/fetchdescriptor/fetchlimit), [Offset](https://developer.apple.com/documentation/swiftdata/fetchdescriptor/fetchoffset) | Exposes ordinary range fetching. It does not establish a stable snapshot or cursor across multiple fetches and concurrent edits. |
| `propertiesToFetch` | Can fetch only selected attributes; reading another attribute later causes additional storage access. Empty means all attributes. [Attributes](https://developer.apple.com/documentation/swiftdata/fetchdescriptor/propertiestofetch) | Choose from actual row/query access after profiling. Complete accepted lexical matching still needs every applicable current field. |
| `relationshipKeyPathsForPrefetching` | Fetches specified related models with the initial fetch, reducing later relationship access. Default is empty. [Prefetch](https://developer.apple.com/documentation/swiftdata/fetchdescriptor/relationshipkeypathsforprefetching) | Avoid repeated category/tag/link fetches where demonstrated, but large related graphs can increase the work and retained data. No blanket prefetch policy is selected. |

Apple describes enumeration's tradeoff: larger batches can reduce I/O at the cost of memory; smaller batches reverse that tradeoff. Its mutation guard throws when dirty context state prevents releasing already-traversed objects, unless escaping mutations are explicitly allowed. This supports a native traversal experiment before custom manual batching, but not a fixed memory guarantee. [SwiftData traversal guidance](https://developer.apple.com/videos/play/wwdc2023/10196/)

`includePendingChanges` defaults to true; false matches persisted state rather than unsaved context changes. Both SDKs also declare `SwiftDataError.includePendingChangesWithBatchSize`. The reviewed symbol page does not describe its operational conditions. Its name alone is insufficient to declare a batching/pending-change combination safe or unsupported. A focused real-store check must establish behavior with unsaved inserts, edits and deletes before choosing a save or overlay policy. [Pending changes](https://developer.apple.com/documentation/swiftdata/fetchdescriptor/includependingchanges), [Declared error](https://developer.apple.com/documentation/swiftdata/swiftdataerror/includependingchangeswithbatchsize)

## Native refresh and cancellation

Query manages fetched models in sync with underlying data. OS 27 ResultsObserver additionally exposes observable FetchResultsCollection results and configurable filter/sort descriptors. Apple documents updates from the same context, other contexts and external changes, including CloudKit. The inspected interface allows changing `filterBy` and `sortBy`; `fetchDescriptor` is read-only. It does not expose an explicit batch-size or moving-window controller. ResultsObserver is a native refresh candidate; it is not proof that every complex related-field query updates within 300 ms. [Query](https://developer.apple.com/documentation/swiftdata/query), [Observable results](https://developer.apple.com/documentation/swiftdata/resultsobserver/results), [Observer](https://developer.apple.com/documentation/swiftdata/resultsobserver)

HistoryObserver reports relevant remote history changes through an observable counter and supports scoping models/authors. It can supply an invalidation signal if architecture uses a derived canonical query, but it does not itself compute the accepted result set or decide when to move selection and scroll anchors. [History observer](https://developer.apple.com/documentation/swiftdata/historyobserver)

The inspected fetch/count/enumerate signatures are synchronous throwing functions. ModelContext explicitly cannot be shared across concurrency contexts; ModelActor supplies isolated execution. Adding an async caller does not itself make synchronous store work preemptible. Swift task cancellation is cooperative. Check cancellation at appropriate boundaries and reject completions from an obsolete query generation when text, filter or sort changes. This is an implementation recommendation, not measured cancellation of a SQLite operation. [Model context](https://developer.apple.com/documentation/swiftdata/modelcontext), [Task cancellation](https://developer.apple.com/documentation/swift/task)

## Sorted, filtered completeness under changing data

The native search report leaves persistent predicate translation to real-store validation. If all accepted constraints and the chosen total order execute in the store, a range fetch can represent a range of the final result. If Foundation matching remains after a coarse store fetch, the first fetched range is only a range of candidates. The sole eligible item can lie beyond it. Continue complete candidate evaluation or use another proven complete query path; an empty post-filtered page cannot mean no matches exist.

Sorting only loaded rows cannot guarantee the full alphabetical, chronological or duration sequence. Unknown placement, locale/collation and stable tie keys must agree between the canonical operation, the store and any subsequent matching stage. No stable order follows merely from specifying one non-unique sort key. Select the exact policies in Duration and search before testing them.

Offset pagination illustrates a changing-data problem. From ordered A/B/C/D, first fetch A/B. Insert X before A, then offset two returns B/C, duplicating B. Delete A instead, then offset two returns D, omitting C. These are logical examples, not SwiftData runtime observations. The reviewed range API does not promise an immutable multi-fetch snapshot. Core architecture must choose whether changes restart the query, update a captured identity sequence or follow another explicit consistency policy. An application-defined cursor is an option only if native results and measured needs leave a demonstrated gap.

Track selection and row identity by stable item UUID rather than array index, name, visible position or membership. Membership changes and shared-label renames can alter matching without changing item identity. A moving window would also need a defined reload policy for earlier rows, anchor restoration, deletion of the selected item and changed sort keys. None is supplied by choosing a numerical window size.

## Smallest useful native comparison

1. Build the complete agreed query over the fixed fixtures and the 5,000-item / 200-list acceptance dataset. Feed the resulting canonical identity sequence to a native List with one row per item. Exercise the eventual Table layout only where it needs columns. Keep expensive matching/sorting outside row bodies. Record store work, matching, identity collection and row rendering separately.
2. If profiling shows model loading or retention causes a target failure, hold the accepted query/rows constant and compare the native batched fetch or ResultsObserver path. Exercise relationships, pending changes, full identity traversal and backward scrolling. Enumeration is an optional native alternative for a complete canonical scan when needed. Use measured batch experiments rather than choose a product page size from the API default.
3. Consider custom paging, identity caching, a moving data window or a different container only for a specific reproduced failure that these native choices cannot resolve. Changing the container cannot repair an incomplete query. A custom design must retain the same complete sorted identity sequence and selection behavior.

This is a proposed downstream experiment, not code or a commitment to a layout/storage topology. Apple's Instruments guidance supports separating long view updates, fetching, hangs, hitches and memory costs rather than attributing every pause to rendering. [SwiftUI performance](https://developer.apple.com/documentation/xcode/understanding-and-improving-swiftui-performance), [Resource measurements](https://developer.apple.com/documentation/technologyoverviews/testing-and-performance)

## Required later tests and measurements

Confirm public query, sorting and loading interfaces under `/tdd` before implementation. Work one failing behavior and its minimal passing implementation at a time. These obligations do not claim passing tests.

| Layer | Required scenarios and expected outcomes |
| --- | --- |
| Query unit tests | Preserve every accepted nine-item set, cumulative groups and cross-field text match. Compare the complete sorted UUID sequence across different realization/batch/window sizes. Include a sole matching item after the initial candidate range. Traversing all results yields the canonical sequence once, without omissions or membership duplicates. |
| Duration and sort unit tests | Test fixed elapsed conversions, the 119/120/121-minute boundary against a 120-minute inclusive maximum, and unknown exclusion/inclusion. Clearing the duration constraint removes its exclusion. Without other constraints, the result returns to the full selected scope. Exercise every required sort direction. Concrete chronological, collation, tie and unknown-position expectations wait for human approval, then must be independent of window size. |
| Real-store completeness | Save/reopen the dataset and compare actual chosen predicates, counts, limits, offsets, batched subscripts and enumeration against the canonical query. Include optional fields and to-many relationships. Verify a match beyond the first range and ensure coarse counts are not displayed as final counts. Pick 1 hour and 31 minutes, save/reopen and preserve 91 minutes without rounding. |
| Real-store mutation | Insert/delete before a boundary; rename shared metadata; edit duration/date/title sort keys; change memberships and states; include pending local changes and imported remote changes. Assert the approved restart/snapshot/cursor policy, no silent omissions/duplicates, correct selection and current canonical fields. Verify ResultsObserver or chosen invalidation behavior on OS 27. |
| Loading and cancellation | Rapidly change text, sort and filters while earlier work is pending. Only the latest generation may replace results. | Memory and scrolling | Record peak/steady memory, allocations, row realization, relationship loading and scrolling hitches during forward/backward traversal.
