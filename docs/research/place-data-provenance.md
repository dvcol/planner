# Place-data provenance

Research for [Place-data provenance](https://github.com/dvcol/planner/issues/5), part of [Native personal planner decision map](https://github.com/dvcol/planner/issues/1). Checked on 2026-10-07. This report resolves the factual investigation; it does not choose the user's capture experience or implement a storage model.

## Finding

The no-key path can preserve useful offline planner data when the user supplies the content independently. It can also preserve map bookmarks and Apple Place IDs. It cannot promise a permanent provider-independent snapshot of every shared place based only on the documentation reviewed here. Shared URL syntax establishes what fields mean, but does not itself establish a retention exemption for provider-generated field values.

Keep independent planner content, provider references, and temporary provider previews separate. The remaining capture choice belongs to [URL and share capture](https://github.com/dvcol/planner/issues/11); the storage boundary belongs to [Core architecture](https://github.com/dvcol/planner/issues/12).

## Verified sources and their limits

### Apple agreement and identifiers

The public [Developer Program License Agreement](https://developer.apple.com/support/terms/apple-developer-program-license-agreement/) defines Map Data broadly, including coordinates and POIs. Attachment 6 permits only limited, temporary storage for the documented service use or performance, followed by deletion, unless Apple grants written permission. It requires corresponding Apple-map display when surfacing Map Data, and Apple maps when plotting it. Sections 2.2 and 2.3 constrain extraction, derived databases, and copying; preserve supplied attribution under Section 2.1. These terms provide no personal-use exception for permanent snapshots. Section 3.3.3 F permits the developer's own data over Apple maps, with alignment responsibility. This is a summary of the agreement text, not a finding about the copyright status of an individual address.

Apple's [Place ID article](https://developer.apple.com/documentation/mapkit/identifying-unique-locations-with-place-ids) expressly exempts Place IDs from the storage restriction. It documents database storage and sharing with other apps. A reference can resolve to current information, fail when a place disappears, or have alternate IDs. IDs alone do not guarantee unique physical places. Private synchronization and backup of those references are a supported design inference from the documented storage/sharing permission; the exemption does not extend to retrieved metadata.

Apple's [agreements page](https://developer.apple.com/support/terms/) dates the public program agreement to August 18, 2026 and says the English agreement accepted in the developer account is binding. The account's accepted version or any separate written permission was not inspected. [Apple test access](https://github.com/dvcol/planner/issues/7) owns checking that account context. Personal registered-device distribution does not remove the service terms reviewed here.

### Apple input mechanisms

[Unified Maps URLs](https://developer.apple.com/documentation/mapkit/unified-map-urls) document `/place` fields `coordinate`, `address`, `place-id`, and `name`. `name` can be a custom card name; it is not proof of a provider's canonical business name. `/frame` and search `center` describe map framing or search bias. Apple's short host is `maps.apple`; the documentation expressly allows recovering a full URL from its HTTP 301 response. This establishes a supported redirect mechanism, not a general license to retain every expanded value.

The archived [Map Links reference](https://developer.apple.com/library/archive/featuredarticles/iPhoneURLScheme_Reference/MapLinks/MapLinks.html) documents older `q`, `address`, `ll`, and search-bias fields. `ll` can be map center or a pin with a label. `q` can be a query, label, or address. Treating any coordinate or query as a verified place would lose that distinction. This older syntax remains useful as an explicit compatibility input, separate from the current unified format.

[MKMapItem](https://developer.apple.com/documentation/mapkit/mkmapitem) supports item-provider reading/writing and coding. This supports decoding a compatible map-item representation when a sender supplies one. It does not promise that Apple Maps supplies that representation on every supported OS or device, and serialization is not a retention exemption. URL/text capture must remain sufficient without that attachment. An object created from independent user content differs from provider-enriched content even though both use the same class.

[MKGeocodingRequest](https://developer.apple.com/documentation/mapkit/mkgeocodingrequest) and [MKReverseGeocodingRequest](https://developer.apple.com/documentation/mapkit/mkreversegeocodingrequest) return map items for address or coordinate inputs. The user's input does not change the origin of the returned fields. The MapKit lookup path also includes [MKMapItemRequest](https://developer.apple.com/documentation/mapkit/mkmapitemrequest) for an identifier. None of these API descriptions establishes a permanent snapshot exemption. Do not substitute an older geocoder merely to assume different retention rights without a specific supporting rule.

### Google links and lookup content

[Maps URLs](https://developers.google.com/maps/documentation/urls/get-started) require no API key. They document launch/search/directions syntax, including `api=1`, `query`, and `query_place_id`. A query can be a name, address, coordinate pair, or broad search. Map `center` is a viewport, not a place pin. The guide is not a general parser contract for Google Maps' `/place/.../@.../data=...` links. [Google's sharing help](https://support.google.com/maps/answer/7101463?hl=en) supports copying and sharing map/location links. Neither source promises unrestricted reuse of provider-produced content inside those links.

The [Maps End User Additional Terms](https://www.google.com/intl/en_us/help/terms_maps/), modified January 27, 2026, restrict copying content, with permissions-page and legal exceptions, and prohibit mass downloads. Do not turn that into a categorical legal conclusion about one bookmarked URL. It does mean that an ordinary shared link is insufficient evidence for a blanket provider-content copying permission.

[Maps Platform terms](https://cloud.google.com/maps-platform/terms), modified August 26, 2026, restrict extraction, storage, and caching outside their express exceptions. These are API-customer terms, distinct from the consumer-link path. They must not be presented as proof that every user-submitted query value is API content.

The current [service-specific terms](https://cloud.google.com/maps-platform/terms/maps-service-terms), modified June 10, 2026, constrain Places API content on non-Google maps and allow only a limited coordinate cache. They also contain a separate, conditional indefinite end-user caching exception for certain Geocoding API address/coordinate fields. That exception does not erase its non-Google-map restriction or establish unrestricted JSON redistribution. [Places policies](https://developers.google.com/maps/documentation/places/web-service/policies) explicitly permit indefinite Place ID storage, distinguish content from IDs, and describe attribution. Provider-specific exceptions must not become a blanket rule for all Google results.

The [Maps Tools Resolution API](https://developers.google.com/maps/ai/grounding-lite/resolution-api) can resolve standard and shortened place URLs to IDs. It requires a billing-enabled project and API-key or OAuth authentication, even though the documented resolution SKU costs zero. [Places setup](https://developers.google.com/maps/documentation/places/web-service/get-api-key) likewise requires billing and authentication. Both are outside the approved no-billing/no-key path. A Google ID is a Google reference, not an Apple Place ID, and cannot be passed to Apple's ID lookup.

## Source-by-field matrix

This matrix is a proposed implementation boundary. "Hold" means the researched sources do not establish the requested durable use; a downstream decision must not silently replace that uncertainty with permission. "Reference" means store a bookmark/identifier rather than materializing a provider metadata snapshot. Display of app-owned coordinates on MapKit does not establish offline availability of Apple's basemap.

| Input/source | Fields | Durable local retention | Private CloudKit | JSON export/import | Native map and offline behavior |
| --- | --- | --- | --- | --- | --- |
| Independent user content, including an app-created link using already owned values | User title, notes, address, coordinates; own link label | Yes, as planner content | Yes | Yes, with original values | Own coordinates can supply annotations. Text works offline; basemap availability is separate. |
| User-pasted or shared Apple/Google link | Original URL and a user-authored label | Reference | Reference | Reference | URL string remains available offline; opening/resolution may need connectivity. No pin without independently available coordinates or a resolved Apple reference. |
| Apple unified or legacy link whose values the user independently authored | Known own values, preserved separately from the URL | Same as independent content | Same | Same | Preserve their meaning; do not convert viewport coordinates to a POI. |
| Apple Maps-generated share URL | Parsed name, address, coordinate | Hold | Hold | Hold | Treat parsed values as candidates, with source tracked. Do not claim permanent offline fields are covered by syntax documentation. |
| Expanded Apple short link | Resolved URL, candidate fields, Apple Place ID if present | Original bookmark; ID permitted; other candidates held | Bookmark and ID only by default | Bookmark and ID only by default | Redirect response can be inspected without scraping a page. Failure still leaves a usable bookmark. |
| Apple Place ID from a documented URL or map item | Opaque ID | Yes, explicit exemption | Yes, reference-sharing inference | Yes, reference-sharing inference | Fetch or show a system place representation when available. Identifier-only records have no guaranteed offline name/address/pin. |
| Apple search, ID lookup, forward/reverse geocoding, or a provider-enriched map-item attachment | Name, formatted/structured address, coordinates, business URL, category, phone, hours, attribution | Temporary service use only under the reviewed terms | Exclude from durable model by default | Exclude from portable data by default | Use the corresponding Apple map. Discard preview when no longer needed. No permanent offline guarantee. |
| Map-item attachment made from known independent content | Own supplied fields | Same as independent content | Same | Same | The class/serialization format does not determine provenance. |
| Google launch URL, possibly after an HTTP redirect | Query text/coordinates and explicit `query_place_id` | Bookmark by default; metadata permission remains unestablished | Bookmark by default | Bookmark by default | Parse documented semantics as candidates. A general query is not a specific result. No Google lookup. |
| Undocumented Google shared URL structure | `/place` slug, `@` coordinates, opaque `data` content, unverified identifiers | Original bookmark only | Bookmark only | Bookmark only | No reverse engineering or HTML extraction. Request missing user content; no automatic pin from camera coordinates. |
| Google Places/Geocoding/Resolution response | Content and IDs | No API call in this charter | Out of scope | Out of scope | API content/ID exceptions do not authorize this app to call those services or overlay their results on Apple maps. |

The independent-content rows describe the absence of a Maps-provider data source, not unrestricted ownership of anything typed or pasted. A user edit or a press of "Save" does not prove an unchanged provider value came from an independent source. Original-link retention is recommended as ordinary bookmarking supported by the sharing mechanisms; it is not permission to extract its contents into a reusable place database.

## Smallest usable import and storage boundary

1. Persist planner UUIDs, user-authored title/notes/location fields, link child records with original URL and optional own label, and an optional Apple Place ID. These are the proposed sources for durable fields in the matrix.
2. Keep an import draft's candidates separately from the saved item. At least its name, address, and coordinates need an origin distinction because one draft can mix manual coordinates with a provider address. `independentUser`, `sharedURL`, and `appleService` are sufficient draft source categories. The architecture ticket should name the actual types.
3. Use original links and IDs as durable provider references. Do not persist the entire `MKMapItem`, encoded attachment, provider response, or redirect body in CloudKit or JSON as an accidental cache. A memory-only preview is the simplest default; no invented 24-hour or 30-day Apple TTL.
4. Resolve an Apple short URL at the documented HTTP redirect boundary. For a Google short link, ordinary HTTP redirect following can be a bounded best-effort transport operation, but there is no verified stable no-key resolution guarantee in the sources reviewed. If it does not produce documented semantics, stop at a partial import. Read no map HTML or opaque provider internals.
5. On offline/failed enrichment, offer the retained link and independently supplied fields, with missing fields absent. Preserve partial capture instead of inventing a location. Existing saved user fields must survive lookup failure.

These are recommendations. The user must decide whether link/identifier-first capture is useful enough or whether a provider clarification is needed to satisfy the original mostly-completed-place requirement. No provider permission inquiry or app implementation was performed by this research.

## Decisions still owned by the map

- [URL and share capture](https://github.com/dvcol/planner/issues/11) must choose the partial/link/identifier capture experience, handling of held URL-derived fields, redirect bounds, and which missing information blocks save. If durable provider snapshots are required, obtain an explicit provider rule or permission rather than declaring user confirmation sufficient.
- [Core architecture](https://github.com/dvcol/planner/issues/12) must define draft versus persisted data, per-field source boundaries, preview disposal, and the common save/export rules. Other control paths must not bypass them.
- [Offline conflicts and recovery](https://github.com/dvcol/planner/issues/10) must preserve provenance through JSON versioning/import and choose how to handle older files with unknown source. Do not silently assume an unknown source is independent.
- [Sync and share prototype](https://github.com/dvcol/planner/issues/15) must verify actual Apple Maps share payloads and extension durability on OS 27 physical devices. The public class's item-provider support does not settle the sender's behavior.

No new ticket is needed for these questions; the existing blockers cover them. If the chosen capture experience depends on durable provider metadata permission, that permission becomes a separate, precise research/task blocker before implementation.
