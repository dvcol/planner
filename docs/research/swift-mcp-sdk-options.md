# Swift MCP SDK options for Q29

Checked 2026-10-08. Primary-source inspection only. No package builds, client connections or new runtime tests were run for this report. This records evidence for Q29 and does not select its protocol baseline.

The official Swift SDK already supports HTTP without transport sessions. Another SDK is not required solely to avoid `Mcp-Session-Id` and return one JSON response per POST. There are also independent native Swift libraries with modern protocol implementations, so a blanket claim that none exist would be wrong. The evidence below does not establish an independently audited alternative.

Three meanings of "stateless" need separate answers:

- **No transport sessions.** The official `StatelessHTTPServerTransport` has no session IDs, returns JSON rather than SSE, and returns 405 for GET and DELETE. The embedding application supplies the HTTP listener. [Pinned transport source](https://github.com/modelcontextprotocol/swift-sdk/blob/0.12.1/Sources/MCP/Base/Transports/HTTPServer/StatelessHTTPServerTransport.swift).
- **Optional legacy initialization.** Official `Server.Configuration.default` sets `strict: false`, allowing ordinary methods before `initialize`. Strict mode requires initialization. Lenient dispatch still uses the legacy protocol implementation and retains initialization state in each `Server` instance. [Pinned server source](https://github.com/modelcontextprotocol/swift-sdk/blob/0.12.1/Sources/MCP/Server/Server.swift).
- **Handshake-free 2026-07-28.** The current published revision removes initialization and protocol sessions. Each request carries version and capabilities in `_meta`; HTTP also validates the version, method and applicable name headers. Servers must implement `server/discover`, although clients need not call it. These requirements are stronger than omitting sessions or accepting an uninitialized legacy call. [Current revision](https://modelcontextprotocol.io/docs/2026-07-28/learn/versioning), [changes](https://modelcontextprotocol.io/specification/2026-07-28/changelog), [transport metadata](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports), [discovery](https://modelcontextprotocol.io/specification/2026-07-28/server/discover).

## Official SDK isolation issues matter more than the label

No session header does not create a separate `Server` or response-routing scope for each client. At 0.12.1, one shared `Server` stores initialization state, client identity, capabilities and negotiated version. A second `initialize` fails with "Server is already initialized", including in lenient mode. Open **PR #257** proposes re-negotiating each initialization; it has not shipped. Lenient mode alone does not fix this. [Pinned server](https://github.com/modelcontextprotocol/swift-sdk/blob/0.12.1/Sources/MCP/Server/Server.swift), [proposed fix](https://github.com/modelcontextprotocol/swift-sdk/pull/257).

The stateless transport also keys response waiters and HTTP contexts by stringified client request ID. Concurrent clients can legally reuse an ID; an assignment overwrites a waiter, leaving a request suspended. Integer `1` and string `"1"` can collide too. **Issue #254** remains open. **PR #264** proposes a private UUID for each HTTP exchange, response-ID restoration and scoped context/cancellation routing. Its author reports passing regression tests, but it remains unmerged and was not run here. Neither release-level mitigation nor safe multi-client behavior was verified. [Pinned transport](https://github.com/modelcontextprotocol/swift-sdk/blob/0.12.1/Sources/MCP/Base/Transports/HTTPServer/StatelessHTTPServerTransport.swift), [issue](https://github.com/modelcontextprotocol/swift-sdk/issues/254), [proposed fix and test report](https://github.com/modelcontextprotocol/swift-sdk/pull/264).

For a simple sessionless JSON HTTP server, the official SDK remains a practical starting point once the intended initialization and concurrent-client behavior is qualified. Full handshake-free 2026 support is a separate choice. Axiom is a concrete native candidate for that choice, with a larger review and runtime verification burden. Cocoanetics deserves another look as its rollout completes. Mgcrea currently has specific protocol and CI gaps.

Stars, recent commits, release claims and passing CI were not treated as proof of external review quality. This was a focused comparison, not proof that no other package exists.
