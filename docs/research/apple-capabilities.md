# Apple capabilities for Planner

Research resolution for [Apple capabilities](https://github.com/dvcol/planner/issues/4), under the [decision map](https://github.com/dvcol/planner/issues/1). Inspected **2026-10-07**. The product baseline is **iOS 27, iPadOS 27, and native macOS 27**, for one person's private iCloud account.

Apple's documented capabilities support the chosen stack. CloudKit supplies eventual replication, not Planner's membership, ordering, conflict, or recovery rules. Calendar export and App Schema integration have permission and contract boundaries that the corresponding human decision tickets must resolve.

This report contains documentary evidence and recommendations. It contains **no compilation, simulator, extension, device, CloudKit, Calendar, or Siri test results**. The access ticket records Command Line Tools as the active developer directory; full Xcode setup and the available physical OS 27 devices remain unverified. [Apple test access](https://github.com/dvcol/planner/issues/7) owns that prerequisite. API introduction versions below come from Apple's documentation availability metadata, inspected on the date above; the deployment floor remains the agreed OS 27 product choice.

## SwiftData and private CloudKit constraints

### Schema compatibility and identity

SwiftData automatic synchronization uses `NSPersistentCloudKitContainer`. Apple's SwiftData guide requires optional relationships, suitable inverses, and excludes the `.deny` delete rule; it also explains why uniqueness cannot be enforced across concurrent distributed writes. [SwiftData synchronization](https://developer.apple.com/documentation/swiftdata/syncing-model-data-across-a-persons-devices)

The backing CloudKit model does not support unique constraints or relationships across different store configurations. Relationships must have inverses. Apple's synchronization technote explicitly excludes ordered relationships. Therefore a Swift array's relationship order is not a durable manual-order contract. [CloudKit-compatible Core Data models](https://developer.apple.com/documentation/coredata/creating-a-core-data-model-for-cloudkit), [TN3164](https://developer.apple.com/documentation/technotes/tn3164-debugging-the-synchronization-of-nspersistentcloudkitcontainer)

**Recommendation for Core architecture:** model order as explicit persisted data and provide a deterministic tie-breaker. Evaluate an explicit membership record when membership needs its own order or identity. Direct many-to-many relationships are supported: Apple's engineer session describes their mirrored join records. This does not guarantee one logical membership when two offline devices independently add it. Persist the brief's app UUID independently of local store row identity; choose duplicate-membership reconciliation in Offline conflicts and recovery. [CloudKit mirroring session](https://developer.apple.com/videos/play/wwdc2019/202/)

Attribute optionality and default values must also be checked against the generated model. Core Data's optional attribute setting and Swift optional types are distinct concepts. A conservative proposal is explicit model defaults where values are required and optional attributes elsewhere, followed by actual CloudKit-container initialization. This is a proposed validation strategy, not a claim that a particular unbuilt SwiftData schema passes. [Configuring attributes](https://developer.apple.com/documentation/coredata/configuring-attributes)

### Timing, conflicts, archive, and deletion

Fetches read the local store; saves commit local data and persistent history. System services later schedule exports/imports. Apple documents throttling and delays without an app-controlled immediate-sync guarantee. A successful local save must not be presented as confirmed remote delivery. [TN3163](https://developer.apple.com/documentation/technotes/tn3163-understanding-the-synchronization-of-nspersistentcloudkitcontainer)

Apple's mirroring session describes last-writer-wins conflict handling. That mechanism cannot decide Planner's intended outcome for simultaneous reorder, duplicate membership, completion versus reopening, or deletion versus edit. Splitting independently editable values can reduce collisions, but requires product-specific decisions and runtime evidence. [Mirroring conflict discussion](https://developer.apple.com/videos/play/wwdc2019/202/)

SwiftData history can preserve selected values after deletion and expose changes from another process. Such history tombstones are not a user-facing trash retention policy. Archive remains a domain state distinct from deletion; recovery, purge, dangling-reference handling, and resurrection prevention remain in the existing decision tickets. [SwiftData history session](https://developer.apple.com/videos/play/wwdc2024/10075/)

### Migration and shared capture storage

Production CloudKit schemas are additive: existing record types/fields cannot simply be removed or have their types changed. Local migration alone does not deploy a cloud schema. Develop and promote the compatible schema deliberately; test old/new local schemas against the same production-compatible cloud contract. [CloudKit model restrictions](https://developer.apple.com/documentation/coredata/creating-a-core-data-model-for-cloudkit), [Schema development session](https://developer.apple.com/videos/play/wwdc2022/10120/)

App Groups supply shared storage, not automatic coordination between app and extension. Apple's extension guidance requires synchronized access and warns that extensions may terminate after completing their request. Capture must have a durable local success boundary; waiting for CloudKit upload is unsuitable as that boundary. [App Group configuration](https://developer.apple.com/documentation/xcode/configuring-app-groups), [Extension scenarios](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionScenarios.html)

Apple's 2026 SwiftData lab discusses shared stores, matching CloudKit capabilities/schema across participating apps, and limited extension time for synchronization. It also describes a separate local shared store as an option. **URL and share capture / Core architecture must choose** direct shared model-store access or a durable capture inbox imported by the app, identify the sync and migration owner, and define replay/idempotency. The report does not prove that opening one SQLite store with differing CloudKit configurations in host and extension is safe. [SwiftData group lab, 21:25](https://developer.apple.com/videos/play/wwdc2026/8017/?time=1285)

## Calendar export boundary

The export remains one-way: Planner stores its canonical schedule. EventKit grants access to the user's Calendar database, not Planner's own domain model.

| Path | What the documented API permits | Implication for the undecided export policy |
| --- | --- | --- |
| Write-only access | Create events; event queries return nothing, including events the app created. A virtual calendar represents the permitted destination rather than an enumerable calendar collection. | It cannot support rediscovering a previous export after relaunch and then updating it. Choose an explicitly create-only behavior if using this permission. |
| Full access | Read, create, edit, and delete Calendar events; inspect available calendars. | Enables lookup/update workflows, subject to stale identifiers and the user's edits. It does not imply bidirectional Planner synchronization. |
| iOS/iPadOS EventKitUI editor | Modern editor can run without granting the app Calendar access. | Useful for user-mediated export; do not assume the app can read the edited event after dismissal. Native Mac needs another UI/API path. |

These distinctions, and the absence of a read-only grant, are documented in [Accessing the event store](https://developer.apple.com/documentation/eventkit/accessing-the-event-store) and Apple's [EventKit/EventKitUI sample](https://developer.apple.com/documentation/eventkit/accessing-calendar-using-eventkit-and-eventkitui). Exact permission and repeated-export behavior remain product choices.

Direct export uses `EKEventStore`, authorization status, the async authorization APIs, `EKEvent`, a selected/default calendar, and `save(_:span:commit:)`. The app must provide title, start/end dates, and calendar, and handle save errors. Usage descriptions are `NSCalendarsWriteOnlyAccessUsageDescription` or `NSCalendarsFullAccessUsageDescription`; sandboxed Mac access additionally needs `com.apple.security.personal-information.calendars`. [Event store API](https://developer.apple.com/documentation/eventkit/ekeventstore), [EventKit permissions session](https://developer.apple.com/videos/play/wwdc2023/10052/)

An `eventIdentifier` can change when an event moves calendars. `calendarItemIdentifier` is local and may be lost during a full calendar sync. `calendarItemExternalIdentifier` can help across devices, but is not unique across imported/shared copies or recurring occurrences, and has Exchange platform differences. A synced identifier alone is therefore insufficient to guarantee repeated-export idempotency. Keep Planner UUIDs canonical and design lookup failure handling explicitly. [Event identifier](https://developer.apple.com/documentation/eventkit/ekevent/eventidentifier), [Local calendar item identifier](https://developer.apple.com/documentation/eventkit/ekcalendaritem/calendaritemidentifier), [External identifier](https://developer.apple.com/documentation/eventkit/ekcalendaritem/calendaritemexternalidentifier)

## App Intents, App Schemas, and identity

Basic custom `AppIntent` actions and `AppEntity` queries can expose Planner operations to Shortcuts and other supported system surfaces. Apple's schemas additionally require matching standardized action/entity contracts. The framework's general `AppSchema` type dates to iOS/iPadOS 18 and macOS 15, while the current Calendar and Reminders domain APIs date to **27**. The system `searchInApp` schema also dates to **27**. Availability of the base type must not be mistaken for availability of each later schema. [AppSchema](https://developer.apple.com/documentation/appintents/appschema), [searchInApp](https://developer.apple.com/documentation/appintents/appschema/systemintent/searchinapp)

Current Siri-facing domains include Calendar, Reminders, Notes, Maps, and System among others. Browser and several document domains are explicitly Shortcuts-only. A native web view does not make Planner a browser-domain app, and a generic planning action does not automatically match a Calendar or Reminders contract. Select candidate schemas only after comparing the resolved domain operation and all required properties; otherwise use a custom intent for its supported surfaces. This report selects no integration actions and promises no unrestricted Siri planning. [App Schema domains](https://developer.apple.com/documentation/appintents/app-schema-domains), [2026 App Schemas session](https://developer.apple.com/videos/play/wwdc2026/240/)

`SyncableEntity` means the entity has an identifier consistent across devices; it is not a data transport. Apple's session separates local store identifiers from stable cross-device identifiers. **Recommendation:** use the persisted Planner UUID for entity lookup, JSON references, and cross-device identity, and keep local persistence handles internal. Verify entity queries after sync, deletion, and duplicate reconciliation. Schema support alone does not prove Siri availability or successful execution on each physical device and system configuration. [SyncableEntity](https://developer.apple.com/documentation/appintents/syncableentity), [App Intents identifiers session](https://developer.apple.com/videos/play/wwdc2026/345/)

## Maps, native web content, and files

Native MapKit covers map presentation, place search, geocoding, and opening Apple Maps. It does not require a Google API account. MapKit search is a server operation; offline saved Planner data must remain usable independently. An Apple DTS engineer states that apps cannot access Apple Maps' downloaded offline map content, preload system tiles through an API, or rely on system tile-cache duration. This closes the offline-map question at a bounded conclusion: **offline Planner records are feasible; guaranteed offline Apple base maps are not an available contract in this plan**. A prototype should observe empty/partial map rendering and present a useful saved-data fallback. [MapKit search architecture](https://developer.apple.com/library/archive/documentation/UserExperience/Conceptual/LocationAwarenessPG/EnablingSearch/EnablingSearch.html), [Apple DTS on offline map tiles](https://developer.apple.com/forums/thread/772258)

`WebView` and `WebPage` are native WebKit APIs available on all three target platforms since OS 26; `WebPage` can manage navigation without a displayed view. They are appropriate for permitted native web content. Remote-page caching, Google URL extraction, and rights to persist provider-derived data are separate questions; this report does not authorize scraping or settle provenance. External Google Maps actions remain the agreed product path. [WebKit for SwiftUI](https://developer.apple.com/documentation/webkit/webkit-for-swiftui), [WebKit session](https://developer.apple.com/videos/play/wwdc2025/231/)

Foundation's `JSONEncoder`/`JSONDecoder` can serialize explicit Codable interchange types. SwiftUI file dialogs support user-selected JSON files; imported URLs require paired security-scoped access/release. Sandboxed macOS requires appropriate user-selected file access. Keep the interchange schema independent of SwiftData's internal identifiers and select merge/replace and version-handling semantics in the portability decision. [JSONEncoder](https://developer.apple.com/documentation/foundation/jsonencoder), [JSONDecoder](https://developer.apple.com/documentation/foundation/jsondecoder), [File importer](https://developer.apple.com/documentation/swiftui/view/fileimporter(ispresented:allowedcontenttypes:allowsmultipleselection:oncompletion:)), [Mac sandbox files](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)

The live documentation already contains OS 27.2 deprecation metadata for `FileDocument` and its exporter overload in favor of newer document/transfer interfaces. **27.2 is currently a beta toolchain**, so this is a future API-review note, not a stable OS 27 requirement or a reason to raise the agreed minimum. Confirm the chosen file API against the installed stable SDK during implementation. [FileDocument](https://developer.apple.com/documentation/swiftui/filedocument)

These checks belong to the named prototype and implementation work. Before coding, the relevant human tickets must record the expected outcomes for undecided cases, and the implementation must agree its public seams under `/tdd`. Documentary evidence alone cannot pass these checks.

| Owner/work | Required scenarios and expected boundary |
| --- | --- |
| Apple test access | Record installed Xcode build/SDK/compiler, signing and CloudKit container access, eligible Mac, and two physical OS 27 devices on one test iCloud account. Do not claim setup from release documentation. |
| Sync and share prototype: schema | Initialize the representative CloudKit-backed model with optional/inverse relationships, persisted UUIDs and order, without uniqueness or ordered-relationship assumptions. Save, terminate, relaunch, and confirm local data survives. Record exact model and diagnostics. |
| Sync and share prototype: replication | On two offline devices create the same logical membership, change completion, edit different and same values, reorder, archive, delete versus edit, and restore. Duplicate, reorder, deletion, and recovery results must match the resolved conflict policy. Record observed latency, not a guaranteed deadline. |
| Sync and share prototype: extensions | Test URL/text capture on iPhone/iPad and Mac with host open and closed, cancellation, termination immediately after local success, concurrent writes, and import replay. | Persistence/migration implementation | Upgrade a seeded prior local schema; run older/newer clients against an additive cloud schema; inspect references, UUIDs, order and recovery data. ## Resolution and remaining decisions

The research questions are closed at the documentary level: a stable OS 27 toolchain exists; the selected persistence, share-extension, mapping, native web, file, Calendar and App Intents capabilities have documented APIs; their limits are recorded above. No unsupported runtime assumption is accepted as proven.

The existing human tickets retain ordering representation, duplicate/conflict/deletion policy, extension-store arrangement, Calendar permission/repeated-export ownership, import mode, and the exact App Intents/App Schema actions. The sharply constrained Calendar choice is create-only export under write-only permission versus an explicit lookup/update contract requiring broader access and recovery. This belongs to the current scheduling/system decisions; it does not require another research ticket.

Next evidence comes from **Sync and share prototype**, after **Core architecture** and **Apple test access** are ready. This report completes research, not those prototypes or their runtime gates.
