# Offline conflicts and recovery

Accepted decision record for [Offline conflicts and recovery](https://github.com/dvcol/planner/issues/10). The human answered R1-R21 on 2026-10-08. R14 replaces the earlier Trash choice with Archive plus confirmed Delete. Implementation and native presentation questions have explicit downstream owners below. This record contains no application code, approved Swift interfaces or executed persistence/CloudKit tests.

## Context and starting state

The private multi-device planner must preserve usable local data offline and after relaunch. CloudKit synchronization is asynchronous. The [Apple capabilities resolution](https://github.com/dvcol/planner/issues/4#issuecomment-6038241318) establishes that automatic mirroring does not supply Planner's uniqueness, ordering, conflict or recovery semantics. It does not prove a particular merge winner, bulk transaction or account-change outcome.

The [Planner vocabulary](planner-vocabulary.md) establishes stable shared identities and live references. [Completion scopes](completion-scopes.md) settles the completion model. Q8 governs every recovery scenario: List/Itinerary completion actions affect only their contextual children, and native global controls belong in the Item view. Global Done OR local Done determines effective completion. Global Reopen retains local values; new local states start Todo; itineraries do not inherit a source list's local completion; Scheduling Q12 gives repeated itinerary appearances independent local completion while preserving those precedence/action rules. Accepted Scheduling Q14 counts effectively Done item appearances out of all item appearances. Archive remains separate.

Accepted requirements include container-only Archive/Delete, ordinary re-addition with local Todo, full JSON backups, add-missing/keep-current default import, locally atomic bulk completion, confirmed referenced-label deletion, manual deletion with reference cleanup, a native same-field conflict winner, preservation of independent edits, rejection of invalid imports together, and independent local recovery across account transitions. R14 establishes Archive plus confirmed Delete with no Trash. R15-R20 settle deletion precedence, membership uniqueness/independent additions, converged ordering, distinct same-name labels, matching container contents on import and explicit separate account recovery. R21 accepts truthful local-save and observed cloud-status presentation; its implementation still requires platform evidence and native UI review. The source tree contains planning documents rather than an app or store.

Accepted A9 in [Core architecture](core-architecture.md) clarifies that backups contain Planner data, excluding device presentation preferences and navigation/selection state. Shared Manual order, completion, references, schedules and planning zones remain backed up. Accepted A12-A14 extend R5/R19 with whole-record Skip/Overwrite, default Skip, dependent-owner skipping and explicitly confirmed restoration. A15 refines R6/import failure wording: validation/database failure leaves the action unapplied; recovery failure after commit retains the complete action and reports incomplete recovery. R21 success still requires both persistence and independent recovery. These follow-ups use sequential numbers rather than the earlier dotted labels.

The human confirmed A12-A15 in the architecture discussion. This extends the original default; it does not replace invalid-file rejection with best-effort decoding or change the native winner for later competing cloud edits.

| Matching X is identical and Z was already imported. | No data change or duplicate. | No data change or duplicate. |
| Current List A has X locally Done; backup A has X/Y in a different order and local state. | Keep current A's full contents/order/local state; eligible new source Y imports independently. | A's contents/order/local state match incoming A. | X is deleted; backup has X, new Z and new B requiring X/Z. | Keep X deleted, skip/report all of B as a dependency conflict and import independent Z. Do not silently remove B's X reference. | Separately preview/confirm restoring X with its stable identity and incoming references; old-lifetime edits/references stay suppressed. | Current W is absent from the file; incoming matching A no longer contains W. | W and current A are retained. | W survives as a source; replacing A detaches only A's W membership. |

| Valid selected import is cancelled or has a genuine validation/database failure before commit. | Selected action remains wholly unapplied after query/reopen. | Same. |

Apply whole-owner dependency handling to new Itineraries, Schedules and owned reference data. The preview shows skipped conflicts, skipped dependents, changed owners and restored identities. Overwrite updates represented live records rather than manufacturing duplicate Items. Only references included in the incoming data are restored; omitted current source entities are never implicitly deleted. Archive/completion remain separate and local contexts outside replaced owners are not rewritten. Reconnect and termination behavior require physical-device proof.

## Accepted sync presentation and retry, R21

The human agreed: report Saved on this device only after local persistence and the independent recovery copy satisfy the approved save contract. Present observed iCloud unavailability or sync failures with useful guidance, using a generic error when the cause is unavailable. Any activity detail describes an observed event; it never asserts every change uploaded, an unsupported pending-upload count or every device being current. Native retries are automatic, with offline use available and no promised deadline or Sync now button.

Navigation prototype owns the exact native presentation; architecture/contracts define the public save/status observations; Sync and share prototype must verify store scoping, account changes, incomplete error detail, relaunch and actual delivery. No per-save cloud receipt or peer acknowledgement is required by this policy.

The future /tdd status fixtures must distinguish a successful store save from the independent recovery-copy checkpoint; neither a copy failure nor an unsaved edit can report the contract's successful save. An available account does not imply uploaded changes. A successful no-change export or an export overlapping a newer local save must not report every change uploaded. Events for an unrelated store must not change Planner's status. An observed failure without quota detail displays a generic useful error. Relaunch does not invent a recent export or hide recoverable local data.
