# Maintenance interruption after native commit

This follows Q155 A through the existing real-store, recovery-filesystem and isolated-process boundaries. Stop a disposable child with SIGKILL from the actual `ModelContext.didSave` notification after maintenance has durably prepared and committed, but before recovery publication. The waiting user command must still have no execution evidence. No production test hook, new declaration, model, target or signing setup is proposed.

First verify that a fresh Planner can see the committed maintenance as pending recovery while the original checkpoint and recovery-file bytes remain unchanged. Then deliver a third independent native membership and create another fresh Planner. It must retain access to read-only pending status and explicit maintenance Retry without acknowledging anything during bootstrap or applying the waiting command.

Retry must publish a complete canonical recovery copy including the later contribution under the original committed maintenance identity. A subsequent ordinary query can perform its own new durable maintenance. Those two acknowledgements keep distinct identities/checkpoints; repeating the original Retry returns its original checkpoint without rewriting files. The waiting command then executes once and replays its exact result. Preserve complete graph/source values, original preparation bytes and truthful unverified file-only inspection.

Observe the actual interruption and public-interface outcome before changing production. Retain raw child ownership, SIGKILL termination, save-notification proof, input/product hashes and any failures. Existing pre-save interruption and recovery regressions remain separate checks. This does not qualify power loss, physical devices, CloudKit or native Mac UI.

## Reproduced failure and correction

The [original runtime failure](evidence/native-membership-consolidation/maintenance-post-save-interruption-red/execution.json) terminates its own child after the actual native save. The parent first verifies the committed maintenance through public pending status. After a third membership arrives, another fresh Planner refuses bootstrap with `maintenanceRequired`: “Prior recovery must complete before consolidation.” No dataset handle exists for explicit Retry. The raw termination record reports SIGKILL, uncaught-signal reason 2 and completion within the 45-second parent deadline; its owned-fixture process identifier matches the actual child.

A [bootstrap-only probe](evidence/native-membership-consolidation/maintenance-post-save-bootstrap-probe/execution.json) advances beyond that refusal. The [saved-command follow-up](evidence/native-membership-consolidation/recovery-relaunch-command-red/execution.json) independently reproduces fresh-bootstrap refusal for membership, expanded-completion and corrected-unproven delivery after a known applied user command. Original failures remain failed and retained.

Bootstrap now reuses the validated read-only recovery observation when consolidation is waiting on prior applied work. Status validates native command/maintenance evidence and requires a complete canonical recovery projection before reporting a known blocked state. A preparation alone, inconsistent evidence or unresolved input cannot admit that fallback. Neither path saves new native maintenance, publishes recovery or runs a waiting command. Explicit Retry retains its existing validation/publication boundary; a later normal query performs any necessary new consolidation. Public declarations, models, portable formats and receipt/fingerprint algorithms are unchanged.
