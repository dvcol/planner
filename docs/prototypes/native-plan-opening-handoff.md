# Directed native plan opening

## Context, starting state and goal

Q122 A and Q126 A approve Open List and Open Itinerary in one foreground main window, preserving every other window's navigation. Previously the app had per-window selections and draft protection but no directed Intent handoff.

Two focused OpenIntent actions now validate the exact saved source and submit an in-memory request. Their dialog says opening was requested and explains a possible draft decision. Neither reports that navigation already happened. The four discoverable create/find App Shortcuts remain unchanged.

## Definition of ready and implementation

The accepted [concrete handoff contract](../native-plan-opening-handoff-contract-review.md) approves the production registration/submission/claim/resolution boundary with real Planner storage. No fake-window callback, test-only dependency, new target, persisted queue or backup field is introduced.

One MainActor coordinator chooses the active main window, retaining activity order when the app becomes inactive. Registering a new inactive window does not displace the most recently focused recipient; never-focused ties use stable window identities. Requests admit exclusively, including while validation is awaiting data. A cold request waits for a ready window. Claiming is exclusive; closing or cancelling its recipient never redirects its draft decision to another window. Additional requests fail with a useful busy explanation.

List source reads do not expose lifetimes. The coordinator therefore uses the existing typed catalog identity sequence and a generation-validated one-row read to bind either plan's exact lifetime. It validates that lifetime and the dataset/ownership namespace again before navigation. A rename or archive retains identity; deletion, replacement data or explicit restoration under a fresh lifetime requires another request. These reads do not establish a storage-performance improvement.

The main SwiftUI WindowGroup uses a per-window UUID value. OpenWindowAction addresses that value when activating or creating the recipient. Window values identify windows, not plans, so changing a plan does not replace another window's navigation. Native appearsActive and scenePhase update registration. Share extensions exclude the app-only coordinator/main-window files.

The recipient waits through an in-progress Save, an existing navigation decision or another presented workflow. An edited New Item uses Save / Discard / Keep editing. Keep editing cancels the opening request. Invalid or failed Save preserves the editor and request; a later valid Save can finish the pending navigation. An applied Save with incomplete recovery cancels opening and retains the existing recovery explanation. After a completed draft decision, the window revalidates before selecting the exact List or Itinerary. New targets clear unrelated contextual selection; no action is silently widened to global Item scope.
