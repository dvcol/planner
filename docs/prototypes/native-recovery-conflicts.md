# Native recovery conflict policies

## Context, before and goal

The native retained-copy journey already proves reviewed additions, Cancel and restoration into a nonempty local dataset. Its source and current records have different identities, so it does not prove Skip or Overwrite when those identities match. R20 requires explicit review before recovery merges; the accepted import policies keep current conflicts under Skip and replace represented records under Overwrite while preserving omitted independent data.

The end state is repeatable native evidence for both policies using the production recovery selection and review form. Current Item notes and a renamed Tag conflict with an independently retained copy. Review must show the exact policy impact, apply only after Restore, preserve logical identities and retain the independent current Item and Tag through relaunch.

## Definition of ready

The approved native recovery contract and Q52 fixture boundary authorize this qualification. The fixture uses real separate local stores, public Core export/import and guarded edits to create conflicts, and the existing production views. No new command, storage schema, provider seam or agent administration is needed. Q83 is independent and remains unanswered.

## Required /tdd and definition of done

- Select the retained copy by its content and verify its Item/Tag identities match the edited current records.
- Review default Skip with two conflicts. Confirm Restore, relaunch and verify the edited Item notes and Tag name remain under their original IDs.
- Select the same retained copy again. Choose Overwrite, review two replacements and the Tag's current/incoming names, then explicitly confirm Restore.
- Relaunch and verify the retained Item notes and Tag name replace the edits under those same IDs, with one visible Item and Tag each.
- Both applications preserve the independent current Item and Tag identities and names. The fixture must not reseed on relaunch.
- Run the existing retained-copy addition/Cancel and export journeys on phone and tablet. Rerun affected journeys after corrections. Inspect original conflict-review and relaunch captures, pass affected lint and compile the Mac fixture app/test host.

This is added regression coverage for existing production behavior, not a new feature claiming a fabricated red/green cycle. If the journey reveals a defect, retain that failure and fix the shared production path before rerunning the affected checks.

## Execution

The new fixture imports the retained Item/Tag through public Core, then edits their current notes/name with field hashes. Independent current Item/Tag records remain outside that incoming copy. Existing stores are reopened without reseeding. The original retained-copy fixture keeps its original nil notes.

The final targeted conflict function passes once on phone and once on tablet, with zero failures or skips. It observes the same retained/current identities, reviews two Skip conflicts, confirms and verifies current values after relaunch, then reviews two Overwrite replacements including the Tag's before/after names. Confirmation restores the retained notes/name under those same IDs. Both policies retain one matching Item/Tag and the independent current IDs/names.

The unchanged export and addition/Cancel functions each pass per device in the preceding regression bundles. The phone bundle also contains the new function's launch-readiness failure and is not a wholly passing bundle; the tablet bundle passes all three. The failure hierarchy shows an Items tab appearing after the navigation helper had selected its sidebar fallback. The only subsequent source change adds an explicit native Items readiness wait at the new function's first launch. Its corrected targeted reruns supply the final conflict qualification. There are three unique passing functions per device across these runs, not one final three-function batch. Earlier initial passing batch logs are diagnostic only.

All eight original captures from the final conflict runs were inspected. Strict affected Swift lint, Markdown lint, whitespace checks and the final Mac fixture app/test-host build pass. Mac has zero runtime functions. Production code, Core/HTTP, storage schema and portable format are unchanged; no new Core/HTTP runs or delivered-file semantic checks are credited.

The execution packet retains final targeted results, complete final capture manifests, selected passing compatibility-function attachments, raw regression results, the launch-failure hierarchy, logs, commands and source/product hashes. Regression attachment manifests intentionally contain only the two credited compatibility functions; the failed bundle's full attachment inventory is not claimed retained.
