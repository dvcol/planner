# Duplicate itinerary completion rows

Two offline-style native rows can describe the same complete expanded appearance: the same List-entry identity/lifetime and membership identity/lifetime. Previously, even fully linked rows made the itinerary unavailable with "The entry has duplicate or inapplicable expanded completion." An explicit Reopen could not make that duplicate graph readable.

Native admission now detects repeated complete contexts before constructing the full snapshot. Isolated staging keeps one valid live row per exact context. Once a duplicate is found, it supplies both that baseline row's observed value and every additional value to the existing binding checks and completion-history resolver. Physical fetch order does not select the completion winner or hide a delivered initial contribution behind existing history. Independent contributions remain available to the existing deterministic history rules; explicit Reopen retains precedence.

Keeping one actual row as the baseline also avoids inventing a Todo initial contribution when both copies are Done. Unknown, incomplete or contradictory bindings still require the existing authority. Complete graph validation, durable preparation and canonical native save retain their current order. Preparation failure rolls back the staged surplus rows before a fresh retry.

No public interface, model, schema, portable format, package, target or test seam changes. The history winner, seed identifiers, canonical persistence and existing scope validation are unchanged. This uses the approved native-input/public Core and real recovery-filesystem boundaries.
