# URL and share capture

Accepted decision record for [URL and share capture](https://github.com/dvcol/planner/issues/11). The human accepted C1-C7 and C8-C16 on 2026-10-08, including the restatement through the question tool. Runtime evidence, exact native presentation and concrete public interfaces have the downstream owners below. This record contains no Swift interfaces, application code or executed capture/extension tests.

## Context and starting state

[Release goals](release-goals.md) makes capture from Apple Maps, Google Maps and Safari part of the first daily-use release on native iPhone, iPad and Mac layouts. The original [product brief](product-brief.md) requires editable partial captures, original links, arbitrary links and sensible plain-text capture. Google billing, API keys and brittle page scraping are outside the agreed charter.

The accepted [Place-data provenance resolution](https://github.com/dvcol/planner/issues/5#issuecomment-6038138633) and its [committed field matrix](https://github.com/dvcol/planner/blob/1bd3772af6259a3ffdca5a10ee2fa5339f8649ff/docs/research/place-data-provenance.md) distinguish independently supplied planner content, durable provider references and temporary provider previews. URL syntax and an unchanged confirmation do not establish unrestricted retention of provider-generated names, addresses or coordinates. The human accepted this link/identifier-first baseline under C1 for the first daily-use release. Captured links can remain useful without a permanent provider metadata snapshot; native preview presentation and actual provider payloads still need prototype review.

The [Apple capabilities resolution](https://github.com/dvcol/planner/issues/4#issuecomment-6038241318) establishes extension APIs and App Group storage, without proving host payloads, simultaneous store access, migration ownership or local save durability. Main currently contains planning documents rather than a runnable app or importer.

[Planner vocabulary](planner-vocabulary.md) fixes shared Item identities and live memberships/labels. [Completion scopes](completion-scopes.md) governs new local Todo contexts and global Done OR local Done display. [Offline conflicts and recovery](offline-conflicts-and-recovery.md) supplies accepted independent recoverable saved data, account isolation, unique memberships, Archive plus confirmed Delete with no Trash, and JSON rejection/identity rules. Its accepted R21 policy permits Saved on this device only after persistence and independent recovery are durable; capture must not assume an upload receipt or automatically change another account's data.

## Goal and expected end state

Produce a human-confirmed capture table mapping each input to its draft, editable fields, user action, retained data, destination references and exact saved Item count. Complete, partial, unsupported, cancelled, interrupted and retried captures need observable outcomes. Include late lookup results and multiple representations without duplicating Items or overriding edits.

The resolution must name future parser/capture/query/store/UI/physical-device fixtures and assign their owners. [Core architecture](https://github.com/dvcol/planner/issues/12) and [Shared command contracts](https://github.com/dvcol/planner/issues/13) define public interfaces, data origins, operation identity, extension/store ownership and bounded redirect policy before /tdd code. [Navigation prototype](https://github.com/dvcol/planner/issues/14) reviews native journeys; [Sync and share prototype](https://github.com/dvcol/planner/issues/15) proves actual payload, local durability, concurrent access and replay behavior.

The human accepted every recommendation below. These decisions settle the baseline save, review, destination, duplicate and multi-input behavior. C8-C16 below settle detailed input classification, conflicting representations, lookup/edit, reuse and save-in-flight policy. | Decision | Concrete situation | Accepted outcome |
| --- | --- | --- |
| C1: Durable capture baseline | Share a Maps link whose provider-produced preview has a name/address/coordinate; go offline after capture. | Save the original bookmark, permitted stable Apple reference if present, and independently supplied planner fields. Keep provider previews temporary, without copying held fields into synced/JSON data. This baseline is accepted for the first daily-use release; provider names, addresses and coordinates are not promised as permanent snapshots. |
| C2: Minimum save fields | An offline short link has no resolved name, address or coordinate. | Allow an editable app-generated title Saved link plus the original bookmark, so missing place details do not block capture. A separately supplied title replaces that fallback. Plain-text-only creation requires nonempty text. |
| C3: Review before save | Paste or share a complete or partial input. | Always show a lightweight editable review with explicit Add/Cancel before creating/linking an Item. No automatic save from parsing, a callback or merely opening the extension. |
| C4: Destinations | Capture from List A versus global capture/Share, then choose Lists A/B. | Preselect the active current list when capturing there. Global capture and Share initially add no list memberships, placing new Items in Inbox; each entry point remembers its own last successful destination per device. Select one or several existing active lists, creating references to one Item, or select no list. Cancel does not change the remembered choice. Missing/archived remembered destinations fall back to no list. Reusing an Item never removes its existing memberships to put it in Inbox. |
| C5: Existing Item candidate | Existing X already retains the same exact original URL; the same link is shared again. | Offer Use existing or Create new, defaulting to Use existing when the candidate is unambiguous. Reuse adds selected missing memberships without silently overwriting X's content, completion/archive or existing local values. No automatic physical-place identity inference from titles/nearby coordinates. |
| C6: Cancellation, durable save and retry | Cancel before Add; fail or terminate during a save; retry the same accepted operation. | Before Add, cancellation/dismissal discards the unsaved draft and late callbacks create nothing. Save success means a durable locally recoverable operation without waiting for upload; the same operation's replay yields one logical result. New capture invocations still follow C5 rather than being silently treated as retries. The architecture must define save/receipt/recovery consistency. |
| C7: Multiple supplied inputs | One provider offers U as URL and text; separately two distinct providers supply U/V. | Alternative formats of U contribute once. One capture invocation produces one reviewed Item, with distinct links retained; it does not batch-create Items or infer a multi-stop itinerary. C9/C10 below settle mixed unsupported attachments and preview selection; contracts define exact loader and review ordering. |

The exceptional loss of both committed-receipt sources after a mirror reset is a separate pending architecture question, not evidence of rollback or automatic retry authority.
