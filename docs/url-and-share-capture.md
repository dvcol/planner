# URL and share capture

Decision record in progress for [URL and share capture](https://github.com/dvcol/planner/issues/11). The ticket is claimed by dvcolomban. The capture choices below are proposals awaiting the human, not accepted product behavior. This record contains no Swift interfaces, application code or executed capture/extension tests.

## Context and starting state

[Release goals](release-goals.md) makes capture from Apple Maps, Google Maps and Safari part of the first daily-use release on native iPhone, iPad and Mac layouts. The original [product brief](product-brief.md) requires editable partial captures, original links, arbitrary links and sensible plain-text capture. Google billing, API keys and brittle page scraping are outside the agreed charter.

The accepted [Place-data provenance resolution](https://github.com/dvcol/planner/issues/5#issuecomment-6038138633) and its [committed field matrix](https://github.com/dvcol/planner/blob/1bd3772af6259a3ffdca5a10ee2fa5339f8649ff/docs/research/place-data-provenance.md) distinguish independently supplied planner content, durable provider references and temporary provider previews. URL syntax and an unchanged confirmation do not establish unrestricted retention of provider-generated names, addresses or coordinates. That report deliberately leaves the link/identifier-first capture experience for this ticket's human decision; it does not silently replace the original mostly-completed-place requirement.

The [Apple capabilities resolution](https://github.com/dvcol/planner/issues/4#issuecomment-6038241318) establishes extension APIs and App Group storage, without proving host payloads, simultaneous store access, migration ownership or local save durability. Main currently contains planning documents rather than a runnable app or importer.

[Planner vocabulary](planner-vocabulary.md) fixes shared Item identities and live memberships/labels. [Completion scopes](completion-scopes.md) governs new local Todo contexts and global Done OR local Done display. [Offline conflicts and recovery](offline-conflicts-and-recovery.md) supplies accepted independent recoverable saved data, account isolation, unique memberships, Archive plus confirmed Delete with no Trash, and JSON rejection/identity rules. Its accepted R21 policy permits Saved on this device only after persistence and independent recovery are durable; capture must not assume an upload receipt or automatically change another account's data.

## Goal and expected end state

Produce a human-confirmed capture table mapping each input to its draft, editable fields, user action, retained data, destination references and exact saved Item count. Complete, partial, unsupported, cancelled, interrupted and retried captures need observable outcomes. Include late lookup results and multiple representations without duplicating Items or overriding edits.

The resolution must name future parser/capture/query/store/UI/physical-device fixtures and assign their owners. [Core architecture](https://github.com/dvcol/planner/issues/12) and [Shared command contracts](https://github.com/dvcol/planner/issues/13) define public interfaces, data origins, operation identity, extension/store ownership and bounded redirect policy before /tdd code. [Navigation prototype](https://github.com/dvcol/planner/issues/14) reviews native journeys; [Sync and share prototype](https://github.com/dvcol/planner/issues/15) proves actual payload, local durability, concurrent access and replay behavior.

## Additional verified platform facts

Checked against current primary sources on 2026-10-08. These add factual detail to the accepted research reports; they do not approve a storage design or count as runtime evidence.

| Area | Primary evidence | Consequence for this decision and later tests |
| --- | --- | --- |
| OS 27 item loading | Apple's [loadItem documentation](https://developer.apple.com/documentation/foundation/nsitemprovider/loaditem%28fortypeidentifier%3Aoptions%3Acompletionhandler%3A%29) and [symbol metadata](https://developer.apple.com/tutorials/data/documentation/foundation/nsitemprovider/loaditem%28fortypeidentifier%3Aoptions%3Acompletionhandler%3A%29.json) specify deprecation at 27.0 and recommend loadObject. The [NSItemProvider reference](https://developer.apple.com/documentation/foundation/nsitemprovider) lists typed loading APIs. | The old extension examples do not select the new importer API. Use an appropriate current typed loader; architecture and affected-target compilation confirm its concrete types/concurrency. Real senders' loadable representations still require device evidence. |
| Items versus formats | [inputItems](https://developer.apple.com/documentation/foundation/nsextensioncontext/inputitems) can be empty. [attachments](https://developer.apple.com/documentation/foundation/nsextensionitem/attachments) is a collection of supplied items; an item provider can offer different representations of its content. | Do not assume one extension item or one attachment covers the request. Alternative formats must not automatically create extra Items. Multiple distinct attachments need an explicit product choice. |
| Text decoding | [UTType.plainText](https://developer.apple.com/documentation/uniformtypeidentifiers/uttype-swift.struct/plaintext) does not specify its encoding. | Do not interpret arbitrary plain-text bytes as UTF-8 by assumption. Test selected typed loaders and malformed representations; a particular host's supplied type remains an observed fact. |
| Extension completion/cancellation | [completeRequest](https://developer.apple.com/documentation/foundation/nsextensioncontext/completerequest%28returningitems%3Acompletionhandler%3A%29) eventually dismisses the extension; its callback Boolean describes expiration. [cancelRequest](https://developer.apple.com/documentation/foundation/nsextensioncontext/cancelrequest%28witherror%3A%29) tells the host to cancel. | Neither is a Planner save receipt or a documented rollback of app writes. Capture must define its own success/cancellation boundary and ignore obsolete asynchronous results. No fixed safe extension execution budget is established. |
| Temporary files and shared access | [loadFileRepresentation](https://developer.apple.com/documentation/foundation/nsitemprovider/loadfilerepresentation%28fortypeidentifier%3Acompletionhandler%3A%29) deletes its temporary file when the handler returns. [Shared-data guidance](https://developer.apple.com/documentation/technologyoverviews/shared-data) requires coordinated access to shared files. | An external temporary URL is not durable capture storage. App Group access does not establish command serialization, migration/sync ownership or exactly-once replay. Architecture chooses the boundary; a real-store/extension prototype proves it. |
| Apple URL meaning | [Unified Maps URLs](https://developer.apple.com/documentation/mapkit/unified-map-urls) documents place fields, viewport center, short-link HTTP 301 expansion, and contextual values my-location/parked-car. | Do not infer a specific POI from a viewport or persist a contextual command as a stable Apple Place ID. The documentation does not provide a universal short path, redirect budget or HEAD guarantee. Keep original URLs during failed/partial resolution. |
| Google no-key meaning | [Maps URLs](https://developers.google.com/maps/documentation/urls/get-started) documents launch/search/directions/viewport parameters without an API key. The accepted provenance report found no stable no-key decoder for opaque shared place URLs or guaranteed short-link enrichment. | Parse supported intent without inventing business data or treating camera coordinates as a POI. Resolution/authentication limitations do not authorize a paid/keyed API or HTML scraping. |

An independent fact-checking agent found these gaps; the applicable primary pages and Apple deprecation metadata were independently read. No OS 27 share payload, loader, importer, extension build, store or termination scenario ran.

## First capture round, pending

All choices below need human answers. The full current frontier includes independent save, destination, duplicate and payload choices; lookup-edit and network-policy details follow the chosen capture model.

| Question | Concrete situation | Recommendation to confirm |
| --- | --- | --- |
| C1: Durable capture baseline | Share a Maps link whose provider-produced preview has a name/address/coordinate; go offline after capture. | Save the original bookmark, permitted stable Apple reference if present, and independently supplied planner fields. Keep provider previews temporary, without copying held fields into synced/JSON data. This is link/identifier-first capture, not a promised permanent provider snapshot. If that cannot satisfy the daily-use journey, investigate the specific durable snapshot permission before implementation. |
| C2: Minimum save fields | An offline short link has no resolved name, address or coordinate. | Allow an editable app-generated title Saved link plus the original bookmark, so missing place details do not block capture. A separately supplied title replaces that fallback. Plain-text-only creation requires nonempty text. Requiring the user to enter a meaningful title before saving is the alternative. |
| C3: Review before save | Paste or share a complete or partial input. | Always show a lightweight editable review with explicit Add/Cancel before creating/linking an Item. No automatic save from parsing, a callback or merely opening the extension. |
| C4: Destinations | Capture from List A versus global capture/Share, then choose Lists A/B. | Preselect the active current list when capturing there. Global capture and Share initially add no list memberships, placing new Items in Inbox; each entry point remembers its own last successful destination per device. Select one or several existing active lists, creating references to one Item, or select no list. Cancel does not change the remembered choice. Missing/archived remembered destinations fall back to no list. Reusing an Item never removes its existing memberships to put it in Inbox. |
| C5: Existing Item candidate | Existing X already retains the same exact original URL; the same link is shared again. | Offer Use existing or Create new, defaulting to Use existing when the candidate is unambiguous. Reuse adds selected missing memberships without silently overwriting X's content, completion/archive or existing local values. No automatic physical-place identity inference from titles/nearby coordinates. |
| C6: Cancellation, durable save and retry | Cancel before Add; fail or terminate during a save; retry the same accepted operation. | Before Add, cancellation/dismissal discards the unsaved draft and late callbacks create nothing. Save success means a durable locally recoverable operation without waiting for upload; the same operation's replay yields one logical result. New capture invocations still follow C5 rather than being silently treated as retries. The architecture must define save/receipt/recovery consistency. |
| C7: Multiple supplied inputs | One provider offers U as URL and text; separately two distinct providers supply U/V. | Alternative formats of U contribute once. One capture invocation produces one reviewed Item, with distinct links retained; it does not batch-create Items or infer a multi-stop itinerary. Selection/primary-location interpretation and mixed unsupported attachments need the next detailed contract. |

## Constructed fixtures and proposed observations

These are readable test aliases and exact inputs for future public interfaces, not agreed Swift signatures or observed physical payloads. Expectations dependent on C1-C7 remain proposed until answered.

- U is `https://maps.apple.com/place?coordinate=35.0,139.0&address=Meeting%20point%20A&name=Picnic&place-id=I521E602783BA9605`. The synthetic fields do not describe the documented specimen Place ID's real place. A provider-shared U has held candidate name Picnic, address Meeting point A and coordinate 35.0/139.0; those candidates are not automatically independent user content.
- S is constructed `https://maps.apple/p/test-link`. Its deterministic HTTP fixture returns 301 with Location U, without fetching a real short link or page body. A failed expansion returns no invented address/coordinate/ID. G is `https://www.google.com/maps/search/?api=1&query=35.0%2C139.0`; B is `https://www.google.com/maps/search/?api=1&query=restaurants`.
- X is an existing shared Item titled Museum idea, with original URL U, global Done + Archived, an A/X membership locally Done and a direct schedule. List B has no X. The fixture tests source/reference scope; identical URLs are only duplicate candidates, not proof that all captures must share X's identity.

## Remaining precise questions and owners

- After C1-C7, finish input classification: plain text, Unicode, malformed/non-web URLs, unsupported/mixed attachments, multiple distinct links and precedence among equivalent or inconsistent representations. Every input class needs an exact prompt, retained text/links and saved count.
- Specify lookup policy, supported provider/redirect hosts, scheme handling and bounded requests/time/redirects/cancellation. Ordinary web bookmarks remain useful without mandatory network enrichment. Documented Apple redirects and best-effort Google handling must not turn into brittle scraping or a metadata guarantee.
- Specify late enrichment versus edited fields, explicit retry, preview disposal, independently supplied location validation and uncertainty display. No hidden automatic content overwrite, completion change, category creation or schedule may follow lookup.
- Architecture/contracts confirm draft versus saved representation, per-field origin, operation identity, duplicate-candidate lookup, account ownership, save/replay receipt and host/extension sync/migration coordination. They must present public boundaries before /tdd tests.
- Navigation prototype reviews native destination/label/duration controls, lightweight review, cancellation/failure and duplicate choices on each device. Categories/Tags remain shared objects; labels with equal names retain separate identities.
- Sync and share prototype records actual advertised/loadable representations from Apple Maps, Google Maps, Safari and text on physical OS 27 iPhone/iPad and native Mac; verifies activation visibility, host closed/open, concurrent access, interruption/replay, local recovery and allowed network fallback. Constructed unit fixtures cannot establish these outcomes.

## Required validation and definition of done

Documentation validation checks affected Markdown, links, final newlines and whitespace. It cannot satisfy Swift unit, store integration, UI or physical-device gates. Code-producing work uses /tdd at confirmed public interfaces, one failing behavior test followed by its minimum implementation, with genuine I/O-boundary stubs and real temporary persistence where appropriate.

- [ ] The human confirms capture, fallback, destination, duplicate, cancellation and replay outcomes, including whether the supported provenance baseline satisfies daily use.
- [ ] Every input and failure case has exact retained data, identity/reference counts, prompt/actions and recovery, or an explicit downstream owner whose human review is required.
- [ ] Redirect/input/late-result contracts are bounded and distinguish primary facts, accepted policy and unproven runtime behavior.
- [ ] Shared capture/save operations and public /tdd boundaries are assigned to architecture/contracts without duplicating business rules across the app, extension and other adapters.
- [ ] Unit/query/store/UI/physical-device fixtures identify concrete before/action/after observations; critical extension outcomes remain mandatory prototype evidence.
- [ ] The resolution links committed source and evidence; the ticket closes only after human decisions and planning criteria pass, with a named pointer added to the map.
