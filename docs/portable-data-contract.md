# Portable data and native recovery contract

Accepted declaration under Contract Q33 A, 2026-10-09, for [Shared command contracts](https://github.com/dvcol/planner/issues/13). Accepted A7/A9/A12-A22 and Q4/Q5/Q11-Q14 govern this format. The [adapter packet](adapter-contract.md), [content catalog](content-and-reader-review.md) and [approved ownership design](architecture-review-packet.md) supply the shared types. Exact field declarations below do not claim that native mirroring, recovery or migration has passed.

## Context, starting state and expected end

Full data-only backup and reviewed Skip/Overwrite behavior are accepted. Previous records name reference/deletion/completion lineage but leave its encoded shape incomplete. This packet declares the portable record graph, validation and native administration results. The expected end is an immutable independently testable version-1 file, faithful empty-store restoration, unchanged receiving device preferences, and precise before/after outcomes for existing stores.

Portable JSON is user data. Internal ownership/receipt/proposal evidence is a separate recovery envelope. Never put account tokens, credentials, control metadata, provider previews, presentation state or an internal receipt into the portable file. Neither MCP nor App Intents exposes these native administration methods.

## Version and common values

The root has exactly `format: "planner-data"`, `formatVersion: 1` and the required arrays listed below. Empty groups use `[]`; omitted groups reject. Version 1 is the only initially supported portable version. Unknown supported-version fields reject with JSON Pointer path. Unsupported versions reject together. Native repeated-property handling follows Q14; parse once into an immutable validated value, then use that same value for preview/apply. There is no extra JSON parser requirement.

UUID parsing, canonical Int64 strings, finite native Date numbers, coordinates/colors and null handling follow the adapter/content declarations. Full records contain every declared optional member using null. Required text is non-whitespace, preserved exactly. Required ID collections are sets by UUID identity, not by name. Source lifetimes are portable data needed for deletion/restoration; an import does not grant a transport caller the right to select an active account/lifetime.

`BoundSource` has exactly `{kind, id, lifetimeId}`, with kind Item/List/Itinerary/Category/Tag/Schedule using lowercase source enum spellings. A record's own `kind/id/lifetimeId` defines the same identity. `BoundIdentity` uses those same three fields and additionally permits membership, itineraryEntry, labelAssociation and ownedLink for closure/restoration metadata. Ordinary new associations use their immutable public ID as lifetimeId, allocating no second ID. Approved original-association Undo is the exception: retain the public ID, issue a new authorized lifetime in a restoration family, and retain the predecessor closure. This distinguishes authorized Undo from obsolete offline references.

`ExpandedContext` has exactly `listEntryId`, `listEntryLifetimeId`, `membershipId`, `membershipLifetimeId`. `CompletionContext` is one of `{kind: "listMembership", membershipId, membershipLifetimeId}`, `{kind: "directItineraryItem", entryId, entryLifetimeId}` or `{kind: "expandedListItem", listEntryId, listEntryLifetimeId, membershipId, membershipLifetimeId}`. Owner/source bindings are resolved from the declared graph. Public appearance IDs remain the approved ID-only variants; Core privately validates these portable lifetime bindings. A global Item flag is not a local completion context.

Each array is a logical set except that rank/tie defines saved order. Producers use deterministic identity ordering for readable stable files. Reordering array serialization alone does not reorder a List. Association/entry UUID ascending breaks equal-rank ties. Source and Schedule IDs are unique within their kind; reference-record IDs are unique within their declared kind. Expanded keys, alias IDs, change IDs and family IDs are unique in their respective groups. Duplicate IDs/keys within a file reject even when the two records look identical. Names may duplicate.

`content` is the declared source content without normalized collections. Item contains `title`, `subtitle`, `notes`, `location`, `estimate`; List contains `name`, `notes`, `color`, `iconName`; Itinerary contains `title`, `notes`, `color`, `iconName`, `location`; Category/Tag contains `name`, `color`, `iconName`. Owned links and label selections reconstruct from their arrays. They are not encoded a second time inside source content. This avoids two conflicting authorities for one reference.

Item requires Bool globalDone/archived. List/Itinerary requires null globalDone and Bool archived. Category/Tag requires null for both. Derived parent completion/progress is absent. Source timestamp values are required finite native Date numbers; caller-created portable files cannot omit them and pretend an exact full backup.

`contentOrigins` records only persisted origin distinctions needed for content/provenance, using optional text/location field names and String `independent` or `appFallback`. Optional nil fields have no origin entry. Required title/name uses `independent` or `appFallback`. Lists/labels/ordinary independently supplied metadata need no new provider field. Core validates permitted field names and origin/content consistency. Provider-held values cannot be declared as a third saved origin. Original-link/provider-reference provenance is established by the owned-link record and accepted validation. This portable declaration is not a writable origin flag in ordinary commands or capture adapters.

Permitted `DeletionTarget` cases are `{kind: "source", source: BoundSource}`, `{kind: "membership", id, lifetimeId}`, `{kind: "itineraryEntry", id, lifetimeId}`, `{kind: "labelAssociation", id, lifetimeId}`, `{kind: "ownedLink", id, lifetimeId}` or `{kind: "expandedCompletion", context: ExpandedContext}`. Schedule deletion uses source kind schedule. Association removal closes the old lifetime; ordinary re-add uses a new public identity. Original-association Undo retains its public identity/state under the new authorized family lifetime; old offline bindings stay closed. Retained closure metadata alone is not proof of the native mechanism.

## Minimal lineage rules

Lineage arrays contain only identity/state needed for accepted consolidation, deletion and restoration. Empty arrays are valid for histories that need none. Do not manufacture aliases, a full audit log or redundant IDs for healthy ordinary records merely to populate the format. When explicit local completion history or duplicate consolidation is present, export the minimal contributions/current changes needed to reproduce its accepted state.

An alias identifies an actual immutable contribution/physical duplicate already used by A17. Membership/direct-entry identity can supply that alias identity where applicable; expanded duplicate contributions use their necessary existing provenance identity. Context/canonical-context bindings must represent the same logical standalone pair or expanded occurrence; intentional repeated itinerary entries are never canonicalized together. Each non-null currentChangeId resolves to that alias's explicit change. Predecessors resolve, are distinct, and form no cycle.

Immutable initial contributions consolidate with OR until a canonical explicit override supersedes them. Explicit later changes do not become new seeds. A causally later change supersedes observed predecessors. Native-selected current changes within an actual record retain Apple's winner; stable change UUID resolves incomparable contributions across physical duplicates. A previously unseen delayed initial alias after explicit Reopen cannot reassert Done. The portable projection retains both effective local flags and necessary lineage; disagreement after canonical validation rejects rather than silently resetting a context. The runtime implementation must prove the approved candidate under both reconnect orders.

A restoration family names the closed predecessor and distinct candidate lifetimes for the same kind/public ID. The stable candidate-lifetime UUID chooses the initial restored version. The selected live record uses that candidate lifetime; references authorized by either candidate resolve within this family. Predecessor references receive no redirect. A deletion with closedFamilyId closes every candidate, including a late unknown loser. A later explicit reviewed restoration starts a new family; an older backup or obsolete edit never creates one automatically. A family and its predecessor closure may coexist with the live restored record. Deleted content is not retained in markers/family metadata.

## Validation and faithful export

Bytes-only decode validates format, every field/type/range, kind restrictions, uniqueness, provider rules and the file's internal reference/lineage consistency before returning immutable `PlannerDecodedBackup`. File-external source references remain explicitly recorded as required bindings. Dataset-bound `prepareReview(session, command)` resolves every such binding against the current authorized planner and validates the complete import graph before any apply. A missing dependency rejects the whole import, not a shortened owner. A deletion target can be absent because its closure remains useful. Lineage IDs must resolve within their declared portable history. This preserves approved `decodeImport(Data)` without letting it guess an account or dataset.

Errors have the adapter Failure shape with code and exact JSON Pointer, such as `/memberships/0/item/id`, `/sources/0/content/title` or `/sources/0/unrecognized`. Structural invalidity rejects the whole file in both modes. Mode conflicts are distinguished after valid decode; they do not convert malformed data into partially accepted input. A persistence failure before commit leaves the entire action unapplied; A15 postcommit recovery failure retains the whole action and reports incomplete recovery.

Export traverses the complete validated logical graph, including archived data and deletion lineage. Unresolved required references or failed reads return export failure rather than a shortened backup. Native `exportData(session)` returns `exported(Data)` or `failed(Failure)`. UTF-8 JSON output has no internal dataset/session/account/control/proposal/receipt fields. Device presentation remains unchanged by import. Exact finite Date/native value reopen and skipped-version migration are runtime tests, not documentation assertions.

## Native import, Delete and recovery forms

`decodeImport(Data)` returns `decoded(PlannerDecodedBackup)` or `invalid(Failure)`. PlannerDecodedBackup has immutable `backup: PortableBackup`, `externalBindings: [BoundSource]` and `originPaths: [BindingPath]`; BindingPath has `binding: BoundSource` and `propertyPath: String`. No dataset is selected by decoding. Native duplicate-property handling is resolved exactly once here. `PlannerCommand.applyImport` contains that value and `mode: skip|overwrite`. Default is skip; changing the mode requires a refreshed review of the new payload/impact. Unresolvable dataset dependencies fail during the bound review and prevent execute.

The native bound review's impact.importDetails contains ImportReview with exactly `imports`, `unchanged`, `skippedConflicts`, `skippedDependents`, `replacements`, `restorations`, `incomingDeletions`, and `referenceChanges`. It does not recursively contain another shared review. Each entry identifies its owner/source, relevant paths/dependencies and the before/after summary. Restorations/incoming deletions have explicit confirmation impact. Review/apply bind the same decoded value, session and target lifetimes; changed current records/targets require a fresh review.

The first six fields are arrays of ImportEntry, exactly `{owner: BoundSource, reasonCode: String|null, dependencies: [BoundSource], propertyPaths: [String], before: OwnerSummary|null, after: OwnerSummary|null}`. OwnerSummary is `{identity: BoundSource, title: String|null, associationIds: [UUID], changedFieldNames: [String]}`; title is the source's name/title display value. Reason codes are `matchingRecordConflict`, `deletedDependency`, `deletedSource` or `unchanged`, and null for unconflicted imports/replacements. IncomingDeletions is `[DeletionImportEntry]`, with exact `{target: DeletionTarget, owner: BoundSource|null, propertyPaths: [String], before: OwnerSummary|null, after: OwnerSummary|null}`. An absent association/context can have unknown owner, represented by null; its declared deletion target still identifies the closure. No owner is fabricated from a removed reference. ReferenceChange is `{change: "add"|"remove"|"retain"|"restore", reference: ReferenceRead}`. Native applied ImportSummary uses the same eight categorized arrays from the actual applied plan, not a new second decode.

Skip keeps the complete current owner, including memberships/entries/order/local state. New independent records import once. New owners depending on a deleted/skipped-unavailable X are skipped completely and reported, rather than shortened. New owners may use a conflicted live current X. Overwrite replaces represented whole-owner data, retaining public identity and creating an authorized restoration family only for separately reviewed deleted-ID restoration. Omitted current sources are never deleted. Incoming markers against live X are conflicts: Skip retains X; Overwrite requires deletion impact. Reimport of identical represented state adds no duplicates. Native import result uses applied/rejected/unverified and recovery exactly as other operations, with the ImportReview categories reflected in the recorded result.

`PlannerCommand.deleteSource` has only `source: SourceReference` restricted to Item/List/Itinerary/Category/Tag. PrepareReview receives that command and issues its token; the enclosing `PlannerOperation` requires the token at execution. Its review lists source/reference removal and preserved shared sources. Native cancellation changes nothing. Delete of a container preserves source Items/Lists. Label Delete detaches every association; the accepted at-least-one-Item confirmation threshold and itinerary-only native presentation remain Navigation prototype obligations. No Trash, timer or restore-from-Trash variant exists.

Approved original-association Undo uses native `restoreAssociation(snapshot:)` with a Core-issued `PlannerAssociationUndoSnapshot` bound to the original removed identity/lifetime, closing operation, dataset and owner/source bindings. Snapshot has `datasetId: UUID`, `ownershipBinding: String`, `identity: BoundIdentity`, `closingOperationId: UUID`, `originalRecord`, and `originalExpandedStates: [ExpandedCompletionRecord]`. Record is the exact removed membership/entry/owned association value, not deleted shared source content. Its bindings must still be live. Snapshot construction is internal; a caller-created dictionary is not an issued snapshot. Core validates current owner/source lifetimes, issues the new authorized restoration family/lifetime and remaps explicitly restored contexts while retaining their saved flags. Ordinary add never uses this snapshot. This is the required representation for the accepted Undo distinction; native presentation/gesture proof stays in Navigation prototype. It is not a persistent Trash or MCP/Intent restoration endpoint.

`inspectRecovery(request:)` uses the approved namespace/proposal read/export method. Request is `namespace(namespaceId:)`, `acknowledgedSnapshot(namespaceId:checkpointGeneration:)` or `proposal(namespaceId:proposalId:)`. Namespace returns `listed(RecoveryView)`; the other cases return `selected(PlannerRecoverySelection)` or `failed(Failure)`. There is no account-selection mutation. RecoveryView has `namespaceId`, recorded `datasetId`, `ownershipDescription: String|null`, `acknowledgedSnapshot: SnapshotSummary|null`, `preparedProposals: [ProposalSummary]`, and `availability: available|unavailable|ownershipUnverified`. A snapshot summary includes schema/format versions, generation and integrity state. Proposal summary includes proposal/original-operation IDs, evidence and requiresFreshReview. It does not present a prepared proposal as acknowledged saved data or change the active account.

Accepted Q36 A adds the native-only `namespaces` request, returning `listedNamespaces([RecoveryView])` ordered by namespace UUID from validated local metadata. An unreadable catalog returns typed failure, never fabricated IDs or successful emptiness. It discovers retained namespaces without selecting an active account or changing data, and remains absent from MCP/App Intents. The [accepted local fixture packet](prototypes/core-local-fixture-review.md) fixes the opening configuration and first store/recovery journey; compilation and runtime proof remain required.

SnapshotSummary is exactly `{storageSchemaVersion: Int64String, portableFormatVersion: 1, checkpointGeneration: Int64String, integrity: "verified"|"failed"|"unverified"}`. ProposalSummary is `{proposalId: UUID, originalOperationId: UUID, evidence: "preparedUnverified", requiresFreshReview: true}`. Namespace/dataset IDs are UUIDs. Native ownershipBinding is a nonempty opaque String generated/validated by the ownership mechanism, not an Apple authentication token or caller-selectable account. Human ownershipDescription is nullable display information; no label string proves ownership.

PlannerRecoverySelection is an immutable Core-issued native value with `selectionId: UUID`, `namespaceId: UUID`, recorded `datasetId: UUID`, `ownershipBinding: String`, `evidence: acknowledgedSnapshot|preparedUnverified`, `checkpointGeneration: Int64String|null`, `proposalId: UUID|null`, `originalOperationId: UUID|null`, `portableData: Data`, and `decodedBackup: PlannerDecodedBackup`. The bytes are the selected data-only backup, decoded once into the accompanying value. Verified snapshot selection requires generation and null proposal IDs; proposal selection requires proposal/original-operation IDs and null checkpoint. Core validates integrity/ownership before issuing it. A dictionary with matching fields cannot manufacture a selection; it is not an MCP parameter. Native file export uses portableData and clearly labels proposal data as unverified.

`PlannerCommand.restoreRecovery(selection:mode:)` contains that selected immutable native value and skip/overwrite mode. The enclosing PlannerOperation session is the explicitly selected target dataset, avoiding a second independently supplied target field. PrepareReview computes the bound ImportReview from that selection, target and mode; execute requires its review token. Empty-target restoration preserves IDs/state; broader merge uses the same exact preview/authority. Never automatically upload old-account data into a new account. Unverified proposal retry uses a fresh operation after review, not the uncertain original operation ID.

`retryRecovery(session, operationId)` is only for a known-applied operation. It retries that checkpoint, never its mutation, and returns the existing applied result with updated complete/incomplete recovery. Unknown/unverified evidence rejects that checkpoint path. It is native/internal recovery work, absent from MCP/Intents administration. Reads/search/export remain available while A18 blocks further domain writes in that dataset.

## Separate internal recovery envelope

The recovery archive has its own `format: "planner-recovery"`, `formatVersion: 1`, `namespaceId`, `datasetId`, opaque `ownershipBinding`, `storageSchemaVersion`, `checkpointGeneration: Int64String`, `portablePayloadBase64`, `dataDigest: String`, `receipts`, and `preparedProposals`. This is not the portable export format.

`portablePayloadBase64` is the exact UTF-8 portable JSON byte payload encoded as base64. `dataDigest` is `sha256:` plus 64 lowercase hexadecimal characters over those exact decoded bytes. This removes ambiguity about whitespace/encoder ordering without inventing another portable JSON canonicalizer. Verify integrity, schema, ownership and graph before inspection/restoration. A digest alone does not prove account ownership or coherent mirroring cutoff.

Receipt has exactly `operationId: UUID`, `payloadDigest: String`, `datasetId: UUID`, opaque `ownershipBinding: String`, `result: AppliedResult`, `commitState: "applied"`, and `checkpointGeneration: Int64String|null`. AppliedResult is the adapter's generated/affected/progress/importSummary object. Null checkpoint means no independent completed checkpoint evidence from that receipt. This is the approved internal receipt, not a general command log. PreparedProposal has exactly `proposalId: UUID`, `originalOperationId: UUID`, `datasetId: UUID`, opaque `ownershipBinding: String`, `proposedBackup: PortableBackup`, `payloadDigest: String`, and `evidence: "preparedUnverified"`; it stays separate from acknowledged payload. Payload digests are Core-issued SHA-256 fingerprints of normalized typed command/ownership bindings; callers never calculate them or use them as credentials. Actual receipt/archive publication follows the approved writer sequence. A database-only committed receipt establishes applied/recovery-incomplete, not R21 success.

### Internal payload fingerprint version 1

Reuse the field-hash tagged value encoding, with a separate prefix: ASCII `PlannerOperationPayload`, zero byte, unsigned 32-bit big-endian 1, then a record containing `command`, `datasetId`, `ownershipBinding`, `resolvedBindings`. Dataset is UUID, ownership is String, and resolvedBindings is an identity set of BoundIdentity records using String kind and UUID id/lifetimeId. Command is the typed normalized command record, with its declared type String and associated fields. This digest uses `sha256-payload-v1:` plus 64 lowercase hex characters. Operation/session/review IDs, access credentials and transport fields are absent.

Normalize creation defaults to their declared full values; edits include only changed fields and their required hashes. Clear uses the field's Optional nil encoding; unchanged fields are absent from the changes record. Extra echoed hashes for unchanged fields are excluded. UUID/Int64/Date/Double/Bool/String/optional/record values use their native tags, not JSON spellings. Declared ordered collections retain logical order; identity sets use the existing sorted-byte encoding. A portable graph inside a native command uses its exact declared fields, sorting logical record-set arrays by their parsed identity/composite key before encoding. Wire numeric civil components convert to Int64; formatVersion converts to Int64. No JSON whitespace/order participates.

Core records the original resolved lifetimes when preparing the operation. Identical replay compares normalized command under that recorded binding and returns its existing result; it does not allocate fresh IDs or re-resolve it as a new mutation. Admission separately revalidates authorized dataset ownership. Review target/impact freshness remains a separate check. A changed payload or binding cannot reuse the recorded receipt. A new internal layout requires a new fingerprint/envelope version, without changing the portable version automatically.

The prototype must prove consistent ownership/cutoff during native account import/reset, atomic archive publication, interruption/relaunch and extension resource limits. Preserve the previous good envelope and withhold success if a coherent new snapshot cannot be established. No custom canonical-store bridge or weakened acknowledgement is substituted.
